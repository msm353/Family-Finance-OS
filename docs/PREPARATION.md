## روش ثبت آزمون

برای هر مورد، commit، محیط (وب یا APK)، نسخهٔ مرورگر/Android، دادهٔ ورودی، نتیجهٔ مورد انتظار، نتیجهٔ واقعی و وضعیت «قبول / رد / انجام‌نشده» ثبت شود. اطلاعات مالی واقعی و فایل کلید یا رمز در repository قرار نگیرند؛ fixtureهای ساختگی و نتیجهٔ مقایسه کافی‌اند. برای آزمون بازیابی، محیط جداگانه با دادهٔ آزمایشی استفاده شود؛ دادهٔ واقعی کاربر جایگزین یا پاک نشود.

## چک‌لیست قبل از تغییر ساختار داده

- [x] **P1 — محیط و مبنا:** شاخه و commit بررسی شوند؛ `npm test`، `npm run lint` و `npm run build` موفق شوند. خطاها ثبت و پیش از ارتقا رفع شوند. هشدارهای audit قبلی جداگانه بررسی شوند؛ ارتقای اجباری وابستگی‌ها بخشی از این مرحله نیست. نتیجهٔ این مرحله در جدول پایین ثبت شده است؛ audit همچنان باز است.
- [x] **P2 — تعیین نیاز به حفاظت از دادهٔ واقعی:** اگر دادهٔ مهم وجود دارد، کاربر محل آن (وب، APK یا مرورگر سیستم قبلی) را مشخص و وجود فایل JSON خارج از فضای برنامه را تأیید کند و سالم‌بودن فایل در محیط جداگانه آزموده شود. اگر دادهٔ مهمی نیست، تأیید کاربر ثبت شود؛ در این مرحله کاربر فقط دادهٔ آزمایشی دارد. این وضعیت به معنی موفقیت Backup/Restore نیست.
- [ ] **P3 — تاریخ و مبلغ قدیمی:** fixture شامل تاریخ میلادی، شمسی با رقم فارسی/عربی، تاریخ نامعتبر، هزینه با توضیح و بدون توضیح، `confirmed: false` و مبلغ اعشاری یا خارج از محدودهٔ عدد صحیح امن بررسی شود. رفتار فعلی و رفتار لازم برای مهاجرت جدا ثبت شوند؛ هیچ مقدار ناسازگاری بی‌صدا اصلاح نشود.
- [ ] **P4 — رفت‌وبرگشت روی وب:** ثبت چند هزینهٔ ساختگی، خروجی JSON، بازیابی در محیط خالی و خروجی دوباره. شناسه‌ها، تعداد، مبلغ، تاریخ نرمال‌شده و سایر فیلدها برابر باشند؛ تغییر طبیعی `exportedAt` در مقایسهٔ داده لحاظ نشود. فایل خالی معتبر نیز آزموده شود.
- [ ] **P5 — رد و لغو:** JSON خراب، نسخهٔ ناشناخته، تاریخ نامعتبر و شناسهٔ تکراری رد شوند؛ لغو تأیید بازیابی داده را تغییر ندهد. محدودیت فعلی حجم فایل و پیام آن آزموده شود.
- [x] **P6 — rollback سرویس پایگاه داده:** خطا در درج پس از clear با دادهٔ ساختگی شبیه‌سازی شود؛ محتویات قبلی پایگاه داده کامل باقی بمانند. آزمون صرفاً parser برای این معیار کافی نیست. سرویس واقعی و transactionهای Dexie با IndexedDB شبیه‌سازی‌شده در حافظه آزموده شدند؛ تأیید روی مرورگر و دستگاه واقعی همچنان در P4 و P7 باز است.
- [ ] **P7 — APK واقعی:** نصب آزمایشی، ثبت آفلاین، ساخت JSON و ذخیرهٔ آن خارج از Cache برنامه، بستن/بازکردن و بازیابی در محیط آزمایشی انجام شود. لغو پنجرهٔ اشتراک، تأیید وجود فایل و انتقال JSON بین وب و APK آزموده شوند. اصلاح‌های بعد از `0.1.2-beta` باید در بستهٔ آزمون حاضر باشند.
- [ ] **P8 — امضای پایدار:** مالک پروژه keystore و پشتیبان امن آن را مطابق [راهنمای امضا](ANDROID-SIGNING.md) آماده کند. وجود چهار secret بدون نمایش مقدار تأیید شود؛ گواهی خروجی با کلید مورد انتظار تطبیق داده شود. بررسی معتبر بودن امضا به‌تنهایی ثابت‌بودن کلید را اثبات نمی‌کند.
- [ ] **P9 — مسیر ارتقا:** APK با امضای ثابت روی نصب تازه آزموده شود؛ ارتقای دو build با همان کلید داده‌های آزمایشی را حفظ کند. انتقال از APK آزمایشی قبلی با JSON ذخیره‌شده بیرون برنامه آزموده شود؛ آزمون حذف/نصب فقط روی محیط آزمایشی انجام شود.
- [ ] **P10 — آمادگی طراحی مهاجرت:** قرارداد schema و فایل نسخهٔ ۲، واحد تومان، شناسه‌های پایدار، ورودی نسخهٔ ۱، رابطه‌ها، حذف نرم و تاریخچه طبق طرح هسته مشخص شوند. fixture ارتقا، اجرای مجدد بدون تکرار و خطای مهاجرت آماده شوند.

## شرط عبور و انتشار

قبل از اجرای ارتقای schema، P1 تا P10 باید شواهد قابل بررسی داشته باشند؛ مورد حل‌نشده با وضعیت باز ثبت شود و مرحله آماده اعلام نشود. طراحی مستندات و fixtureها می‌تواند در این فاصله ادامه پیدا کند.

پس از پیاده‌سازی اولین برش، آزمون‌های نمونهٔ مالی، مهاجرت، بازیابی نسخه‌های ۱ و ۲ و حفظ گزارش‌ها و ورودی شمسی دوباره روی کد جدید اجرا شوند. برای انتشار، شمارهٔ نسخهٔ package و Android، `versionCode`، یادداشت انتشار و فایل مورد استفادهٔ workflow هماهنگ شوند؛ tag فعلی `v0.1.2-beta` دوباره استفاده نشود.

workflow انتشار `android-release.yml` ساخت را همراه انتشار انجام می‌دهد؛ اجرای `workflow_dispatch` آن برای صرفاً آزمایش خروجی مناسب نیست. مسیر جداگانهٔ `android-test.yml` برای ساخت debug با نام FFOS Test و شناسهٔ نصب جدا اضافه شده است؛ دستی یا با push روی `develop` و پیام آخرین commit دارای `[android-test]` اجرا می‌شود. فقط artifact می‌سازد و انتشار یا کلید release نیاز ندارد. نتیجهٔ اجرای CI در P7 ثبت می‌شود. مسیر آزمون امضای ثابت و ارتقای نسخهٔ اصلی همچنان به P8 و P9 وابسته است.

بررسی تکمیلی P3 و بخش parser از P5 با import مستقیم `makeExpenseBackup` و `parseExpenseBackup` و assertionهای Node در حافظه اجرا شد؛ فایل آزمون جدیدی اضافه نشد و پایگاه داده‌ای خوانده یا نوشته نشد. این بررسی جای آزمون خودکار ماندگار مهاجرت، restore پایگاه داده یا آزمایش UI را نمی‌گیرد.

در ۲ اکتبر ۲۰۲۶، شش آزمون ماندگار در `tests/backupDatabase.test.mjs` اضافه شدند. `npm test` اکنون هر دو فایل آزمون را با tsx اجرا می‌کند؛ fake-indexeddb فقط وابستگی توسعه است و داده‌ها را در حافظهٔ فرایند Node نگه می‌دارد. تمام ۹ آزمون، lint و build پس از این تغییرات موفق شدند؛ `git diff --check` نیز خطا نداشت. هیچ دیتابیس مرورگر یا APK باز یا تغییر داده نشد. اجرا در sandbox با `spawn EPERM` متوقف شد و اجرای مجاز خارج از sandbox موفق شد. نصب ابزارهای آزمون همچنان سه هشدار audit متوسط گزارش کرد؛ رسیدگی به آنها جداگانه باز است.

## شواهد آزمون مرورگر، ۲ اکتبر ۲۰۲۶

- محیط آزمون نشانی جداگانهٔ `http://127.0.0.1:4187` بود؛ هنگام شروع هزینه‌ای نداشت. دادهٔ مرورگر اصلی، وب میزبانی‌شده و APK خوانده یا تغییر داده نشد.
- fixtureهای کوچک و کاملاً ساختگی در `tests/fixtures/backup-browser` نگهداری می‌شوند. فایل بزرگ فقط در `node_modules/.tmp/ffos-browser/oversized.json` ساخته شد و وارد Git نمی‌شود.
- خروجی واقعی `ffos-backup-2026-10-02.json` در Downloads شامل دو هزینه و مبلغ کل ۲۰۰٬۰۰۰ تومان است. تاریخ‌های خروجی `2024-03-20` و `2024-03-21` هستند؛ رابط پس از بازیابی آنها را `۱۴۰۳/۰۱/۰۱` و `۱۴۰۳/۰۱/۰۲` نشان داد.
- بعضی کلیک‌های بازیابی خطای زمانی کنترل مرورگر دادند، ولی مشاهدهٔ بعدی پیام موفقیت و نتیجهٔ پایدار را نشان داد. رویداد دانلود ابزار نیز به مهلت زمانی رسید، اما وجود فایل واقعی و محتوای آن روی دیسک مستقلاً بررسی شد. این محدودیت‌های ابزار به عنوان خطای برنامه ثبت نمی‌شوند.
- آزمون لغو انجام‌نشده است؛ مشاهدهٔ موفقیت بازیابی یا وجود `window.confirm` در کد اثبات عملکرد لغو نیست. منطق برنامه برای دورزدن این محدودیت تغییر نکرد.

### آزمون دستی باقی‌ماندهٔ لغو

۱. فقط محیط آزمون `127.0.0.1:4187` را باز کنید و وجود دو هزینهٔ «آزمون خوراک» و «آزمون خرید» را ببینید.
۲. از بخش پشتیبان، فایل `tests/fixtures/backup-browser/empty-v1.json` را انتخاب کنید. پیش‌نمایش باید صفر هزینه در فایل و دو هزینه در برنامه نشان دهد.
۳. «بازیابی داده‌ها» را بزنید و در پنجرهٔ تأیید مرورگر **لغو** را انتخاب کنید. اگر پنجره قابل کنترل نیست، نتیجهٔ لغو همچنان باز بماند؛ آن را موفق فرض نکنید.
۴. صفحهٔ خانه را باز و reload کنید؛ هر دو هزینه و مبلغ کل ۲۰۰٬۰۰۰ تومان باید باقی مانده باشند. پیام موفقیت بازیابی نباید ظاهر شده باشد.
۵. محیط، نتیجه و مشاهدهٔ پنجره را در P5 ثبت کنید. دادهٔ این نشانی ساختگی است و در صورت تأیید اشتباهی فایل خالی، با fixture `legacy-v1.json` یا فایل دانلودشده قابل بازیابی است.

بازبینی UI یا اجرای dev جای آزمون بازیابی و حفاظت داده را نمی‌گیرد. پس از تکمیل لغو در P5، کارهای باز بعدی APK، امضای پایدار، مسیر ارتقا و قرارداد دقیق schema هستند؛ این آزمون وب به معنی پایان فاز آماده‌سازی نیست.
